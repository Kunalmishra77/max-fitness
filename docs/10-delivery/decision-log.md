## ADR-010 — Supabase Postgres (Mumbai), no local Docker
2026-09-10 · Accepted · **Context:** the development machine cannot run Docker, and the blueprint assumed a local `postgres:17` container plus Testcontainers for integration tests. **Decision:** use managed **PostgreSQL 17 on Supabase, `ap-south-1` (Mumbai)** as the database for development, accessed **only through Prisma** — no `supabase-js`, no anon key, no service-role key, no Supabase Auth/Storage/Realtime. `DATABASE_URL` is the Supavisor **transaction** pooler (:6543, pool max 5) for the `apps/web` runtime via `@prisma/adapter-pg`; `DIRECT_URL` is the Supavisor **session** pooler (:5432, pool max 3) for `prisma.config.ts` migrations, the seed script and the pg-boss worker. Optional `SHADOW_DATABASE_URL` (separate empty project) covers the case where the Supabase role lacks `CREATEDB`; optional `TEST_DATABASE_URL` (separate project) runs integration tests, which skip with a message when it is unset. CI runs integration tests against a Postgres 17 **service container**. `infra/docker/compose.dev.yml` is not created; Dockerfiles, Caddy and VPS scripts move to Phase 8.

**Verified against current official documentation (10 Sep 2026), not from memory:**
- Supabase's Prisma guide assigns the **transaction** pooler (:6543) to `DATABASE_URL` for serverless/auto-scaling runtimes and **session** mode (:5432) to migrations — matching the split above.
- Prisma's PgBouncer guide: the Schema Engine "is designed to use a single connection to the database, and does not support connection pooling with PgBouncer", so migrations must use a direct/session connection. It also **recommends against** setting `pgbouncer=true` for PgBouncer 1.21.0 or later, and driver adapters such as `@prisma/adapter-pg` bypass the flag.
- Supabase's Prisma troubleshooting page confirms Supavisor **transaction mode does not support prepared statements**. `@prisma/adapter-pg` uses node-postgres, which issues unnamed queries, so no flag is required. This is proven with a live query at Step 3; adding `pgbouncer=true` to `DATABASE_URL` is the documented fallback.
- Prisma 7 **removed the `directUrl` datasource property**; the migration URL is now `datasource.url` in `prisma.config.ts`, and **`shadowDatabaseUrl` moved into `prisma.config.ts` too** (it lived in `schema.prisma` up to Prisma 6). Our config therefore sets `datasource.url = env("DIRECT_URL")`.
- `prisma migrate dev` needs `CREATEDB` on the connecting role to build its shadow database; providers that forbid creating databases require a manually provisioned one via `shadowDatabaseUrl`. `prisma migrate deploy` needs no shadow database.

**Verified on the live Supabase project (2026-09-11):** Mumbai (`aws-0-ap-south-1`) session pooler on :5432 and transaction pooler on :6543; PostgreSQL 17.6; the connecting role is `postgres` — not superuser, with CREATEDB; Supabase's `anon` role exists. Through the transaction pooler, Prisma 7.10 with `@prisma/adapter-pg` ran 11 parameterised queries (5 sequential, 6 concurrent) with no prepared-statement errors and **no `pgbouncer=true`** — the assumption above is now confirmed, not inferred.

**Consequences:** unit tests must never touch a database; the seed must batch its writes because every round trip crosses the internet; Supabase's auto-generated Data API must be neutralised (ADR-011); production database hosting is re-decided in Phase 8 and nothing in the app depends on the answer.

## ADR-011 — RLS enabled on every public table, with no policies
2026-09-10 · Accepted · **Context:** Supabase auto-generates a PostgREST **Data API** over the `public` schema, callable with the project's anon key. Our tables would otherwise be readable by anyone holding that key. **Decision:** the first migration runs `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` on **every** table the application creates in `public`, with **no policies**, and every later migration does the same for new tables. Additionally, `public` is removed from the Data API's exposed schemas in the dashboard (manual). **Why it is safe:** PostgreSQL table owners bypass RLS unless `FORCE ROW LEVEL SECURITY` is set, and our Prisma role owns the tables — so the application is unaffected — while the `anon`/`authenticated` roles PostgREST connects as match zero rows. pg-boss is unaffected because it lives in its own `pgboss` schema, which the Data API does not expose. **Consequences:** a migration that forgets the `ALTER TABLE` silently exposes a table, so it belongs on the migration review checklist and in the pre-launch security checklist.

## ADR-012 — TypeScript 6.0.x, not the `latest` TypeScript 7

## ADR-013 — Fee state is canonical in TypeScript; `v_member_fee` is a read-model
2026-09-10 · Accepted · **Context:** `database-design.md` §4.1 defines `v_member_fee` using `now()`, which conflicts with CLAUDE.md §2.2 (inject a clock, never call `new Date()` in domain code) and with `testing-strategy.md` §2 ("tests must not rely on `now()`"). **Decision:** `feeState(today, membership...)` in `packages/core` is the single canonical implementation. `v_member_fee` stays as a fast read-model for list queries and dashboard counts only, and an integration test diffs it against the core function over the same fixtures at fixed dates. **Consequences:** no business decision (a reminder, a call task, a kiosk greeting) is ever taken from the view alone; if they disagree, the view is the bug.

## ADR-014 — Fee state ignores a non-contiguous future membership
2026-09-10 · Accepted · **Context:** BR-4.2 derives fee state "from the membership covering today or the latest ended one", and adds "If an upcoming membership starts the day after, use its end date". `v_member_fee` instead takes the confirmed membership with the greatest `endDate`, which would report `PAID` for a member whose membership ended in March and who has a booking starting next January. **Decision:** core takes the membership covering today; failing that, the latest **ended** one; and it extends the effective end date through a future membership **only when that membership starts within one day of the current end** (a genuine renewal chain). This is the literal reading of BR-4.2, not a new rule. **Consequences:** the view carries the same guard; documented as a known divergence risk in the view/core diff test.

## ADR-015 — `ReminderRule.offsetDaysTo` is authoritative for the post-expiry cap
2026-09-10 · Accepted · **Context:** the cap exists in two places — `settings.postExpiryMaxDays` (BR-5.2, default 7) and `ReminderRule.offsetDaysTo` on the `POST` rule (schema, `null` = no limit). **Decision:** `offsetDaysTo` is what the engine evaluates; it is written from `postExpiryMaxDays` whenever settings are saved, and settings validation rejects a state where the two disagree. **Consequences:** one query path, no drift; the settings screen stays the owner-facing control.

## ADR-016 — BR-2.3 "effective per month" reading
2026-09-10 · Proposed (display only; owner may adjust) · **Context:** BR-2.3 says "`floor(pricePaise / durationMonths)` rounded to nearest ₹10", which specifies two conflicting roundings. **Decision:** the displayed figure is `round(pricePaise / months / 1000) × 1000` paise — e.g. ₹4,000 ÷ 3 = ₹1,333.33 → **₹1,330**. ## ADR-018 — `/api/v1/health` reports the worker heartbeat
2026-09-10 · Accepted · **Context:** `api-specification.md` §3 specifies `{ ok, db, version }`, but the worker is a separate process with no inbound ports, so its liveness is only observable through the `WorkerHeartbeat` table the schema already provides. **Decision:** extend the response to `{ ok, db, worker: { ok, lastBeatAt, ageSeconds }, version }`, with `worker.ok` false when the last beat is older than **3 minutes** (the threshold the schema comment states) and top-level `ok` false if either component is down. No secrets, no counts. **Consequences:** Uptime Kuma gets one URL covering both processes; `api-specification.md` §3 is updated to match.

## ADR-019 — Toolchain pins: ESLint 10 with eslint-plugin-import-x; project-local pnpm store
2026-09-11 · Accepted · **Context:** (1) `eslint@9.39.5` installs with an upstream "no longer supported" deprecation, so the 9.x line is end-of-life. `eslint-plugin-import@2.32.0` caps its peer range at ESLint 9, and `eslint-config-next@16.3.4` depends on it. (2) The developer's global pnpm config sets `storeDir` to `D:\dev-cache\pnpm-store` while the repo lives on `E:`; hardlinks cannot cross volumes, so pnpm byte-copied every package and a first install ran for well over an hour. **Decision:** (1) pin **ESLint 10.10.0** and enforce the folder-structure import boundaries with **`eslint-plugin-import-x@4.17.1`** — a maintained, ESLint-10-native fork exposing the same `no-restricted-paths` rule named in `folder-structure.md`. `eslint-config-next` is dropped: the flat config never loaded it, and Next-specific lint rules can be added later via `@next/eslint-plugin-next` if wanted. TypeScript stays at 6.0.3 (ADR-012). (2) `storeDir: E:/.pnpm-store` in `pnpm-workspace.yaml` (pnpm 11 reads settings there, not from `.npmrc`), leaving the global config untouched. Packages allowed to run install scripts are listed explicitly under `onlyBuiltDependencies` (Prisma, esbuild, Tailwind oxide, unrs-resolver). **Consequences:** a developer on a different drive layout should adjust or remove `storeDir`. On Linux (CI) the value is not a drive path; pnpm is expected to treat it as a repo-relative directory named `E:`, which is git-ignored — **unverified until the first CI run**, and the fallback is to override the store in `ci.yml`.

## ADR-020 — Extensionless relative imports in TypeScript source
2026-09-11 · Accepted · **Context:** workspace packages are consumed from TypeScript source, not from a built `dist` (`transpilePackages` in `apps/web/next.config.ts`). The first `next build` failed with 52 "Module not found" errors: Next 16's Turbopack does not map a `./foo.js` specifier onto `./foo.ts` inside those packages, although `tsc`, Vitest and tsx all do. **Decision:** relative imports in `apps/*` and `packages/*` omit the file extension (`./constants`, not `./constants.js`). This is the form `moduleResolution: "Bundler"` (set in `tsconfig.base.json`) is designed for, and every tool in the stack resolves it. **Consequences:** the packages cannot be run by plain Node ESM without a loader or bundler — which is already the case, since nothing in the repo executes untranspiled TypeScript; the worker runs under tsx, and the Phase 8 container build bundles it. Revisit only if a package is ever published or executed as raw ESM.

## ADR-021 — `sm` is 360px: the first multi-column layout starts at `md`
2026-09-11 · Accepted · **Context:** `design-tokens.json` defines `breakpoint.sm = 360px`, and `tokens.css` maps the breakpoint tokens onto Tailwind v4's `--breakpoint-*` variables, as it does for every other token group. That overrides Tailwind's default `sm` of 640px, so any `sm:` utility applies on every supported phone. The Phase 1 Foundation page used `sm:grid-cols-2` and rendered two columns at 360px, clipping content. **Decision:** keep the token as designed (design docs are the source of truth, CLAUDE.md §1). `sm:` therefore means "all supported phones" and adds nothing over the unprefixed class; multi-column layouts begin at `md:` (768px), and `lg:` (1024px) / `xl:` (1280px) match Tailwind's defaults. **Consequences:** UI code and copied shadcn-style components must not rely on `sm:` as a tablet breakpoint; review any imported component's `sm:` classes when it is restyled to tokens. Every screen is still checked at 360px (CLAUDE.md §2.10).

## ADR-022 — Landing data: tagged `unstable_cache`, HTML rendered per request
2026-09-11 · Accepted · **Context:** TRD §4 asks for the landing page to be static with ~5-minute revalidation, refreshed by tag when the owner changes prices, promo or settings. In Next 16 the tagged `'use cache'` directive requires `cacheComponents: true`, which changes rendering rules app-wide (dynamic APIs need Suspense boundaries), and `revalidateTag` now takes a cache profile as a second argument. The page also shows date-dependent content — today's hours row and "Open today till…" — and a fully static build would need database access at `next build` time, which CI does not have. **Decision:** data (plans, gym settings) is read through `unstable_cache` with tags `plans` and `settings` and a 300-second revalidate; the HTML renders per request from that cached data. `revalidateLandingContent()` calls `revalidateTag(tag, 'max')` for the CRM to use when settings change (Phase 4) — there is no public revalidation route. If the database is unreachable, sections that need it render their designed fallback rather than failing the page. **Consequences:** freshness matches the TRD (≤ 5 min, instant on tag); render cost is a cached read, not a query; revisit `cacheComponents` when the rest of the app is ready for it.

## ADR-025 — `cn()` knows the design-token scales
2026-09-11 · Accepted · **Context:** `cn()` runs tailwind-merge, which recognises Tailwind's default scales only. It read token utilities such as `text-display-l` or `text-body` as text colours, decided they conflicted with `text-brand-plate-navy` or `text-brand-white`, and silently dropped one. Section headings rendered at body size, and red buttons lost their white text (axe: 4.49:1 and 3.56:1 on Signboard Red). **Decision:** `apps/web/src/lib/cn.ts` uses `extendTailwindMerge` with the token names for `text` (font sizes), `leading`, `radius`, `font` and `ease`. A unit test pins the combinations that broke. **Consequences:** a new font-size, line-height or radius token must also be added there; the test fails loudly if a size and a colour stop coexisting.

## ADR-030 — Hero LCP: poster first, video after load; narrow client imports
2026-09-11 · Accepted · **Context:** the first Lighthouse CI run on the production build measured mobile LCP at about 5.0 s against the 2.5 s budget (CLS 0, accessibility passing). The LCP element was the hero `<video>`, mounted at hydration and painted seconds later under CPU throttling. The poster `<img>` painted early but did not count: the flat placeholder AVIF was 953 bytes over 412×640 px, under Chrome's low-entropy threshold for LCP candidates. Separately, the lead form imported the `@mfp/shared` root, shipping the env schema and date helpers to the browser, about 90 KB of unused JavaScript. **Decision:** (1) the hero mounts video only after the window `load` event and an idle callback, so the poster is always the first large paint and later video can no longer become the LCP. (2) Placeholder hero media carry a faint static grain, and AVIF posters are encoded at CRF 18. Their entropy is then comparable to a real photo, so the budget measures what real posters will do. The grain is placeholder-only; real footage replaces the files by name. (3) `@mfp/shared` declares `sideEffects: false` and exports `./schemas/lead`; client components import narrow entry points, never the package root. (4) The second Lighthouse run showed the poster *loaded* by about 1.5 s but *painted* about 3 s later, behind hydration, plus a large parse/style/layout task. So the first slide's posters are preloaded from `<head>` per orientation with high fetch priority and decoded synchronously. The FAQ uses native `<details>`/`<summary>` instead of the Radix accordion from the Phase 2 plan: keyboard and screen-reader behaviour comes from the browser, and one hydrated island and its library leave the page. `@radix-ui/react-accordion` stays installed pending a CRM need. **Consequences:** video starts a moment after load, with the poster showing until then; any new client-side import from `@mfp/shared` should use a narrow export. This machine's CPU benchmark index is about 1,000–1,300, below the high-end desktop Lighthouse's 4× slowdown assumes, so local results are somewhat pessimistic. The budget is not relaxed for that; CI numbers are the reference.

## ADR-034 — Payment confirmation: one core path, two row locks, webhook as source of truth
2026-09-11 · Accepted · **Context:** Phase 3 has three ways a payment can be confirmed: the browser's checkout callback, the Razorpay webhook and the DEMO_MODE pay dialog. They can arrive in any order, or at the same moment (cases P1–P3), and the receipt series must have no gaps (BR-11.2). **Decision:** (1) All three end in `confirmPayment()` in `packages/core`, in one transaction. `PrismaPaymentConfirmationUnitOfWork` takes `SELECT … FOR UPDATE` on the payment row first, so a second arrival waits, then reads `PAID` and returns `ALREADY_CONFIRMED`. The receipt and member-code counters increment with `INSERT … ON CONFLICT DO UPDATE … RETURNING`, which locks the counter row until commit, so a rolled-back confirmation gives its number back. (2) `verifyCheckout` checks the HMAC first, then reads amount and status from the gateway's own record (`GET /v1/payments/{id}`), never from the request. It confirms only `captured`; `authorized` returns `PENDING`, and the page polls `/checkout/status` until the webhook lands. (3) The webhook verifies the HMAC over the raw body before parsing, and records each event in `WebhookEvent` (unique `provider+externalId`; the `X-Razorpay-Event-Id` header, else `event:paymentId`). An event recorded but never processed (the process died, or confirmation threw) is **not** treated as a duplicate, so Razorpay's retry is processed. A payment for an order this system never created is marked processed with `PAYMENT_NOT_FOUND` and answered 200. Signature failures return 401. (4) An amount mismatch (P4) leaves the payment `CREATED` with `failureReason = AMOUNT_MISMATCH`, activates nothing, and queues `alert.owner {kind: PAYMENT_AMOUNT_MISMATCH}`; the member sees `NEEDS_REVIEW`, not "failed". (5) `payment.failed` sets a `CREATED` payment to `FAILED` only, never a paid one (Razorpay does not guarantee event order). A later capture on the same order still confirms, because Razorpay allows retries within an order. (6) In DEMO_MODE the webhook route returns 404: the simulator's "signature" is a fixed marker, so accepting webhooks would let anyone confirm a payment. The pay dialog (`POST /checkout/simulate`, which needs the member's token) completes the simulated order and returns Razorpay-shaped callback fields, and the browser posts them to the real `/checkout/verify`. (7) The existing outbox event types are reused: owner alerts are one `alert.owner` type with a `kind` in the payload, and enrolment is `kiosk.enroll`, whose dispatcher checks face consent and minor status. **Verified:** integration tests P1–P8 against PostgreSQL. With `FOR UPDATE` removed, P3 fails with two `CONFIRMED` outcomes, a double activation. **Consequences:** anything that confirms money later, such as the CRM desk payment, must go through the same locks and counters.

## ADR-043 — The enquiries pipeline in the CRM
2026-09-12 · Accepted · **Context:** enquiries have been arriving since Phase 2 — the website's lead form writes them, raises the owner's bell alert and queues a WhatsApp alert, and the worker's `lead-followup` job raises a `NEW_LEAD` call task for anything untouched for two gym hours. ## ADR-045 — Four rules the CRM was skipping

## ADR-049 — Changing your own PIN
2026-09-14 · Accepted · **Context:** ADR-048 let the owner manage everyone else's login, but deliberately not an owner's own PIN — and the launch checklist (security-plan §6) says every PIN is set by the person who uses it, with the demo owner PIN `2468` gone before real use. **Decision:** (1) **"मेरा PIN बदलें" is open to every role**, from "और" and from the staff screen. ## ADR-050 — A member's data: export and erasure
2026-09-14 · Accepted · **Context:** privacy-and-dpdp-compliance §6 promises members a copy of their data within 15 days and erasure within 30, both done by the owner from the CRM with a PIN. The permission matrix already had `member.export`; nothing used it, and there was no way to erase anyone. The plan says what erasure deletes and what it keeps, but not how each table is treated. **Decision:** (1) **Two separate capabilities, `member.export` and `member.erase`**, both owner (and super-admin) only and both needing a PIN entered in the last five minutes. (2) **Export is `GET /crm/members/{id}/export`, a JSON download** in a versioned format (`max-fitness-member-export/1`): profile, memberships, payments, attendance, consents, messages and call notes. ## ADR-055 — Photos and receipts in a private Supabase Storage bucket, over S3
2026-09-16 · Accepted (client: "bucket is S3 … supabase use karenge S3 ke liye"; library chosen by the client: AWS SDK v3) · **Context:** on Vercel the local driver writes to one function instance's `/tmp`, and the end-to-end run against production proved the consequence: a desk photo saved by one instance came back 404 from another (ADR-054). ## ADR-056 — Importing the paper register (Phase 5, first slice)

## ADR-065 — The owner's digest and alerts, and one record of an alert rather than two (Phase 6, fourth slice)
2026-09-23 · Accepted · **Context:** whatsapp-automation-engine §8 asks for a digest at 08:30 and owner alerts "immediate, bundled if > 3 within 5 min", and T9/T10 fix their wording. The app already wrote an `Alert` row *and* an `alert.owner` outbox event in the same transaction for a payment, an enquiry and an amount mismatch — and nothing ever consumed the outbox events, so they sat `PENDING` and grew. **Decision:** (1) **The `Alert` row is the record.** It is written in the same transaction as the thing that happened, which is all a transactional outbox gives you, so the second copy was removed along with the `alert.owner` event type. A new `Alert.notifiedAt` column (migration `20260923064226_alert_notified_at`, with an index on `gymId, notifiedAt, createdAt`) says whether the owner has been told. (2) **"Bundled if more than three in five minutes" is a ration, not a delay.** `planOwnerAlerts` clusters the pending alerts by arrival — the window measured from the first alert of a cluster, never chained along, or a trickle three minutes apart would hold the first alert back for ever — and counts the alert messages already sent inside the window against the same budget of three. Past it, the cluster becomes one message naming the first three and counting the rest. Each alert message is keyed `alert:<id>`; a bundle is keyed by its whole sorted cluster, so the same burst dispatched twice is one message. (3) **Sentences are built by us, from rows.** Nothing a member typed reaches the owner's WhatsApp as free text, a mobile is masked even on its way to the owner (the number to call is in Max Register), money is formatted from paise, and every sentence is one line — a WhatsApp template variable is rejected if it holds a newline, and the T10 body is a single variable. An alert whose subject has since been deleted is stamped rather than retried for ever; a backlog older than six hours is stamped without sending, because an alert about a visit three days ago is not news. (4) **The digest says nothing on a day with nothing to say.** An owner who is sent "0, 0, 0, 0, 0" every morning stops reading the message that matters. Its counts come from the same `member_fee_at` read model the CRM home screen reads, yesterday's money is bounded by the IST day (a UTC window would misreport every evening after 5:30, pinned by an integration test), and a member whose fee ends today is counted under "ending today" and deliberately *not* again under "this week". A `JobRun` claim makes a repeated 08:30 fire a no-op. (5) **The kill switch means all of them.** An owner who hits "stop all automatic messages" — most likely because WhatsApp has flagged the number — does not want the gym still sending, so the digest is skipped and alerts are held, not dropped. (6) **Both jobs send through `sendTemplate`**, the same logged-then-sent path as every other transactional message, rather than growing a second route to WhatsApp; `memberId` is null, because a digest belongs to the gym rather than to anybody's record. (7) **T11 `mf_birthday_wish` is registered** (marketing category) and `buildBirthdayWish` is keyed by member and year; BR-8.2 keeps sending it an owner's tap, which is the next slice. **Consequences:** the owner's phone tells them what the gym did without becoming noise. **Still to come in Phase 6:** the birthday send button, the quality auto-pause and slot failure guard, reminder settings, the Message Simulator, E2E journey 8 and the live-send checklist.

Each message is rendered with the same `renderTemplate` the send uses, into a WhatsApp-style bubble, so the preview cannot quietly differ from what a member receives. (2) **One query, not one per day.** A forecast assumes nothing changes, so each member's latest membership and end date are read once from `member_fee_at(today)`; the calendar walk is pure. Unlike the live slot query, it does *not* drop members who cannot be messaged — "nobody on the 3rd" and "four people, none of whom agreed to WhatsApp" are different answers, and the screen should be able to tell them apart. (3) **The per-number cap is applied per day, across slots** (BR-5.6), not inside each slot as `planSlot` does: a family that used up the morning must not get another round in the evening. (4) **It is labelled a forecast** — nobody renews, unsubscribes or joins in it — and it writes nothing at all; the renew and unsubscribe tokens in it are `#` placeholders, because minting thirty days of signed links for a screen nobody acts on would put working links where they are not wanted. (5) **"Advance time" is not built.** §10 describes a fake clock that executes slots and replays inbound taps. It mutates the demo data and needs the worker running, which it is not; the read-only plan gives the demo its "watch the journey" value without that risk. Recorded as deliberately deferred. **What it found on its first run:** against the seeded demo data the plan is **2,806 messages in 30 days**, because the `POST` rule fires at all three of its slots (09:30, 14:00, 19:00) for each of its seven days — 21 messages to one member whose fee has run out. That is what BR-5.1 and the engine doc's own cost estimate describe, so nothing was changed here, but it is a WhatsApp quality risk and a decision for the client: POST once a day for seven days would be 7 messages instead of 21. Raised with the client on 2026-09-23.

## ADR-068 — POST reminders once a day, not three times (2026-09-23)
2026-09-23 · Accepted (client decision) · **Context:** the Message Simulator's first run against the demo data reported **2,806 messages in 30 days**, with 77 on day one. The cause was the shape of the `POST` rule as BR-5.1 originally wrote it: slots 09:30, 14:00 and 19:00, every day of its seven-day window, so one member whose fee ran out received **21 messages in a week**. The engine doc's own cost estimate assumed exactly that. It is not a bug; it is a rule that reads fine in a table and badly on a phone. **Decision:** the client chose **one POST message a day, at 19:00, for the seven days of the cap — 7 messages instead of 21.** Evening, because that is when a member would have come to the gym and when they read WhatsApp. Changed in `REMINDER_RULE_DEFAULTS`, the BR-5.1 table, the worker's `REMINDER_SLOTS` and `SLOT_RULE_CODES` (the 09:30 and 14:00 crons are gone, since no rule uses them), the test builders, and the stored `ReminderRule` row of the demo gym. The per-rule tests now assert that POST fires at 19:00 *and not* at the two slots it used to share, so a revert cannot pass quietly. The cost estimate drops from ≈650 to ≈500 utility messages a month. **Consequences:** the projected plan for the demo data falls by roughly two thirds. A member is chased once a day for a week rather than three times a day, which is the difference between a reminder and a nuisance — and the practical difference between keeping the gym's WhatsApp number in good standing and losing it. The owner can still change the slots per rule from Settings; the reminder settings screen (next slice) is where the three-a-day shape could be recreated, so that screen should warn rather than allow it silently.

## ADR-069 — The two safeguards, and the bug that would have stopped every reminder (Phase 6, seventh slice)
2026-09-23 · Accepted · **Context:** whatsapp-automation-engine §9 asks for two guards before live sending: pause the `POST` rule when Meta signals a quality problem, and stop a slot where more than 20% of sends fail. **Decision:** (1) **Both guards are blunt on purpose.** They stop sending and tell the owner; neither tries to work out *why*, because by the time either fires the thing that knows why is Meta, and the only safe move is to stop pushing. What they do **not** stop matters as much: a receipt, a welcome and a pre-expiry reminder are messages the member is expecting, so only the chasing after expiry is paused. (2) **Quality guard.** `isQualitySignal` names four Meta codes — 131049 healthy-ecosystem hold, 131048 spam-rate, 130472 experiment group, 131056 pair-rate. A plain undeliverable (131026) is deliberately *not* one: that is one member's number, not the gym's standing, and pausing every lapsed member's reminder over it would be wrong. The guard disables the POST rule conditionally on it still being enabled, so Meta repeating the same error for forty messages in a bad batch produces one pause and one alert, not forty. (3) **Failure guard.** More than a fifth of a slot's sends failing stops the slot, but only once at least five have been attempted — one failure out of two is 50% and means only that one message failed. The counts come from the message log rather than a running tally, so a worker that restarts mid-slot sees what the one before it saw. The run row carries `status = 'STOPPED'`, which every message still queued for that slot reads before sending and logs as `SKIPPED:SLOT_STOPPED`. Stopping happens before the alert and does not depend on it: an alert that cannot be written is not a reason to let the rest of the slot go out. (4) **`SendIntent` now carries `businessDate` and `slot`.** The guard has to know which run a failure belongs to, and carrying the two fields is honest where parsing them back out of the idempotency key would be fragile. **The bug this slice found:** `PrismaSendContext.load` — the query `sendReminder` makes for *every* message — filtered on `MessageLog.businessDate`, a column that **did not exist** in the schema or the database. Prisma's generated `where` type did not catch it, so lint, typecheck and the whole unit suite were green while every reminder send would have thrown `PrismaClientValidationError` at runtime. It was never noticed because the worker has not run in production and no integration test covered that query. Fixed by adding the column the domain always meant to have (`businessDate DATE`, indexed with `toNumber`, migration `20260923101240_message_log_business_date` with a backfill from `createdAt` in IST — a UTC date would have put an 11 pm message on the wrong day), setting it in `PrismaMessageLogWriter` (the callers were already passing it), and pinning the query with `send-context.integration.test.ts`, which fails loudly if it ever breaks again. **Consequences:** the reminder engine can actually send. Two integration tests that still asserted the removed `alert.owner` events (ADR-065) were corrected to assert the `Alert` rows instead — they had stayed green in the unit suite because they need a database.
