# QR Onboarding Flow — Technical Spec

PRD: QR-01…06 · Business rules: BR-3.6, BR-13.

## 1. The QR code
- Encodes: `https://{domain}/qr?src=reception&g={gymSlug}&utm_source=qr&utm_medium=poster`
- Static URL (the poster never needs reprinting); versioned by `src` for analytics (`reception`, `counter2`, `flyer`).
- Generated by `infra/scripts/generate-qr-poster.ts` (library: `qrcode`), error correction level **Q**, quiet zone 4 modules, min printed size 6 × 6 cm, SVG output for print.
- Poster spec in `assets/reception-qr/README.md`. Demo environment uses a staging URL poster marked "DEMO".

## 2. Screens & routes
| Route | Purpose |
|---|---|
| `/qr` | Language toggle + two big choices |
| `/qr/existing` | One-question-per-screen wizard |
| `/qr/new` | Reuses sign-up components with `source=QR_NEW`, adds "Pay at reception" as equal-weight option |
| `/qr/done/[ref]` | Big reference code + "Show this at reception" |

## 3. Existing customer wizard
| Step | Field | Notes |
|---|---|---|
| 1 | Mobile | OTP if `settings.features.otpRequired` |
| 1b | Lookup | `POST /qr/lookup` (after OTP) → imported members on this number (name + masked plan end) → "This is me" or "Someone else" |
| 2 | Full name | Prefilled if matched |
| 3 | Gender | |
| 4 | Date of birth | |
| 5 | Selfie | Same component as sign-up |
| 6 | Current plan | 1 / 3 / 6 / 12 / Not sure |
| 7 | **What is your month-end date?** | Required; calendar opens on current month; range today−60 d to today+13 months; helper text |
| 8 | Last amount paid | Optional numeric |
| 9 | Consents | Same as sign-up |
| — | Submit | `POST /qr/existing` |

Server behaviour:
1. Create/merge member: if matched imported member → attach selfie/consents to that member; set status `PENDING_VERIFICATION` only if not already `ACTIVE`-verified; else create new member `PENDING_VERIFICATION`, `source=QR_EXISTING`.
2. Create `VerificationRequest` with `referenceCode = Q-####` (random, unique per gym, not sequential).
3. Alert + call task `VERIFICATION_PENDING` (if not decided within 2 h).

## 4. Verification in CRM
Approve → transaction:
- `Membership(CONFIRMED, isDeclared=true, declaredEndDate, endDate=approvedEndDate ?? declared, startDate per BR-3.6, pricePaise=declaredAmount ?? 0, source=QR_EXISTING)`
- Member → `ACTIVE`, `memberCode` assigned if missing
- Outbox: `mf_verification_approved`, kiosk enrolment job (if consent), audit
Reject → reason required; member stays `PENDING_VERIFICATION` with `rejected` flag; soft-deleted after 7 days.

## 5. Abuse controls
- Rate limits (API spec §8), OTP optional, Cloudflare Turnstile (or similar privacy-friendly challenge) invisible on submit if abuse detected.
- Reference code shown to staff prevents someone else's submission being approved blindly.
- Declared data never activates reminders until approval.

## 6. Migration drive plan (operations)
1. Import paper register via CSV (CRM Import) — name, mobile, gender, plan, month-end date.
2. For 2–3 weeks, staff asks every arriving member to scan once; target 20–30/day.
3. Daily: owner clears Verify queue (1 tap each when register match exists).
4. Week 3: call remaining imported-but-unconfirmed members; mark left where appropriate.
